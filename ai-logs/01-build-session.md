## Development Summary

The AI-assisted development process covered the following areas:

### 1. Project Planning

The initial design focused on separating **natural-language reasoning from financial and business-critical decisions**.

The core principle was:

> **The LLM handles language and intent; deterministic application code makes the final financial decisions.**

This ensures that payout amounts, limits, approvals, and payment actions are controlled by explicit business rules rather than generated by the model.

### 2. Data and Policy Analysis

The provided policy, trip data, conversation examples, and PaySwift sandbox behaviour were reviewed before implementation.

Important findings included:

* Trip timestamps needed to be interpreted according to the required timezone.
* Duplicate trip records were present in the supplied data.
* Distance values required unit conversion before being used for payout calculations.
* Some rider identifiers were malformed.
* PaySwift could return different HTTP responses for payment requests.
* A timeout response could occur even when the payment was actually recorded.
* Rate limiting could affect subsequent PaySwift requests.

These cases were incorporated into the implementation and testing strategy.

### 3. Core Business Logic

The project implementation included deterministic components for:

* Payout calculation
* Payout limits
* Auto-payment eligibility
* Approval requirements
* Settlement handling
* Payment reconciliation
* Idempotency
* Error handling

The financial logic remains outside the LLM so that the same input always produces the same business decision.

### 4. Agent and Tooling

An agent-based workflow was implemented to handle user conversations and decide when application tools were required.

The agent can use tools for operations such as:

* Looking up trip information
* Calculating or checking payouts
* Checking payment status
* Requesting or processing approval
* Interacting with the PaySwift sandbox
* Reconciling payment results

The agent does not directly calculate or invent financial values. Instead, it uses the application's deterministic tools and returns the results in natural language.

### 5. API and Application Layer

The project includes an API layer that connects incoming requests with the agent, business logic, tools, and persistence layer.

The application is responsible for:

1. Receiving the request.
2. Identifying the conversation or event.
3. Passing relevant information to the agent.
4. Allowing the agent to invoke the appropriate tools.
5. Executing deterministic business rules.
6. Persisting relevant state and transaction information.
7. Returning a structured response.

### 6. Payment Integration

The PaySwift sandbox was integrated for payout processing.

The implementation accounts for:

* Idempotent payment requests
* Payment status handling
* Timeout scenarios
* Failed requests
* Reconciliation
* Ledger consistency

A particularly important case is when a payment request times out but the payment may still have been recorded by the payment provider.

The system therefore does not blindly retry such requests. It uses reconciliation and idempotency information to determine the actual payment state before taking further action.

### 7. Testing and Evaluation

The project was tested using the provided sample conversations together with additional edge cases.

Testing covered:

* Normal payout requests
* Boundary conditions
* Amounts above the automatic-payment limit
* Approval-required payments
* Duplicate events
* Payment failures
* Payment timeouts
* Reconciliation scenarios
* Invalid or incomplete input
* Agent/tool interactions

The final evaluation included the complete sample set plus additional scenarios.

## Model Testing

The real-model evaluation was performed using:

**Primary model:** `openai/gpt-oss-120b` through Groq

**Fallback model:** `openai/gpt-oss-20b`

During real-model testing, several issues were identified and addressed, including:

* Invalid tool-call formatting
* Token-quota exhaustion
* Model fallback behaviour
* Responses that did not consistently include required identifiers

The prompts and application flow were updated so that the final responses followed the required output behaviour.

## Final Validation

The final evaluation covered:

* 24 provided sample conversations
* 5 additional scenarios
* **29/29 scenarios passing on the final evaluation**
